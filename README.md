# DID PANAS — інтернет-магазин грибної продукції

Професійний вітрина + адмін-панель для українського грибного бренду Did Panas.
Побудовано з нуля на Next.js 16 (App Router, Cache Components / PPR), React 19,
TypeScript, Tailwind CSS v4, shadcn/ui. Референсний сайт використано лише як
натхнення: власні тексти, власний дизайн, жодного копіювання CSS/коду/бренду.

## Швидкий старт

```bash
npm install
cp .env.example .env.local   # потім заповніть значення
npm run dev                  # http://localhost:3000
```

Для production:

```bash
npm run build
npm start                    # http://localhost:3000
```

### Змінні середовища (`.env.local`)

| Змінна | Призначення |
| --- | --- |
| `ADMIN_LOGIN` | логін до `/admin` |
| `ADMIN_PASSWORD` | пароль до `/admin` |
| `ADMIN_SESSION_SECRET` | випадковий рядок (≥32 символи) для HMAC-підпису cookie сесії |
| `NEXT_PUBLIC_SITE_URL` | публічний URL для sitemap, canonical і og-тегів |
| `NOVA_POSHTA_API_KEY` | ключ API Нової пошти для автопідказків на `/checkout` (опційно) |
| `CLOUDINARY_CLOUD_NAME` | Cloudinary Dashboard → Product Environment Credentials → Cloud name (рекомендовано для production) |
| `CLOUDINARY_API_KEY` | API key того самого акаунта Cloudinary |
| `CLOUDINARY_API_SECRET` | API secret (лише сервер, ніколи не `NEXT_PUBLIC_`) |
| `R2_ACCOUNT_ID` | альтернатива: Cloudflare R2 → Overview → Account ID (використовується лише якщо Cloudinary не налаштовано) |
| `R2_ACCESS_KEY_ID` | ключ API-токена R2 з правами Object Read & Write |
| `R2_SECRET_ACCESS_KEY` | секрет того самого токена (лише сервер, ніколи не `NEXT_PUBLIC_`) |
| `R2_BUCKET_NAME` | назва бакета зображеннями |
| `R2_PUBLIC_BASE_URL` | публічний base URL для читання (без сліда в кінці) |

Локальні креди для розробки: логін `admin`, пароль `DidPanas2026!` (у `.env.local`).

### Доставка та Нова пошта

- Чотири способи доставки: **Нова пошта — відділення**, **Нова пошта —
  поштомат**, **Курʼєр Нової пошти**, **Самовивіз із майстерні**.
- Самовивіз завжди безкоштовний, для решти діє поріг безкоштовної доставки
  (`freeShippingThreshold`) і ціна доставки (`shippingCost`) з **Налаштувань**.
- З міста, вулиці, відділення та поштомата автопідказки приходять із
  `GET /api/nova-poshta/{settlements,streets,warehouses}` — це серверні
  route handlers, які викликають `POST https://api.novaposhta.ua/v2.0/json/`
  з методами `searchSettlements`, `searchSettlementStreets`, `getWarehouses`
  (fallback: `getCities`, `getStreet`). Ключ передається лише в тілі запиту
  на сервері.
- Без `NOVA_POSHTA_API_KEY` route відповідає `503 { unavailable: true }`,
  поле перемикається у **ручний режим** з підказкою «Довідник Нової пошти не
  налаштовано.» — замовлення все одно оформлюється. Магазин працює без ключа.
- На сервері (`lib/actions/orders.ts`) перевіряються формат і належність
  переданих ідентифікаторів міста/відділення/поштомата до обраного міста;
  повна адреса (вулиця, будинок, квартира) чи назва відділення зберігаються в
  `customer.address` / `customer.warehouse` і показуються на сторінці
  замовлення та в адмін-панелі.

## Як додати товар

1. Увійдіть в адмін-панель: `/admin` → логін/пароль із `.env.local`.
2. Відкрийте **Товари → Додати товар** (`/admin/products/new`).
3. Заповніть поля:
   - **Основне**: назва, артикул (SKU), вага/обсяг, короткий опис, повний опис;
   - **Склад і зображення**: склад, походження, фото (перше фото — головне в
     картці; для товарів без фото застосовується брендова ілюстрація);
   - **Ціна та склад**: ціна, стара ціна (необовʼязково, для знижки), залишок
     у штуках, категорія, наявність, бейдж, «показувати в добірці на головній».
4. Натисніть **Зберегти** — товар зʼявиться в каталозі (`/catalog`), у пошуку та
   в sitemap.

Редагування: **Товари → Редагувати** (кнопка в рядку таблиці).
Видалення: кнопка **Видалити** на сторінці редагування або в рядку таблиці
(запитує підтвердження). Залишок автоматично зменшується після оформлення
замовлення.

## Як додати банер

1. Увійдіть у `/admin`.
2. Відкрийте **Банери → Додати банер** (`/admin/banners/new`).
3. Заповніть: заголовок, підзаголовок, **три зображення** — десктоп, планшет,
   мобільний (показуються через `<picture>` за брейкпоінтами
   640/1024 px), текст кнопки (`До каталогу`), адресу кнопки (`/catalog`),
   колір акценту, порядок, прапорець «активний».
4. Натисніть **Зберегти** — банер зʼявиться на головній сторінці: позиція
   `hero` — великий банер над добіркою, позиція `promo` — картка-банер у
   добірці. Якщо зображення не задані, застосовується текстова/ілюстративна
   заміна.

Банер-герой на головній використовує файли з `public/images/banners/hero-{desktop,tablet,mobile}.png`
(оригінали — у `banner/`), задані в `data/seed.ts`.

Видалення: кнопка **Видалити** під карткою банера в списку або на сторінці
редагування. Неактивні банери не показуються й не потрапляють у sitemap.

## Інші розділи адмін-панелі

- **Огляд** (`/admin`) — статистика, останні замовлення, позиції з малим
  залишком, швидкі дії.
- **Категорії** — назва, slug, порядок, опис; керують фільтром у каталозі.
- **Замовлення** — список і сторінка замовлення, зміна статусу
  (нове → підтверджене → оплачене → відправлене → завершене / скасоване).
- **Налаштування** — назва магазину, слоган, контакти, години роботи, вартість
  доставки, поріг безкоштовної доставки, соцмережі та юридичний дисклеймер;
  нижче — **Статус фотохмарки** (режим сховища: Cloudinary / R2 / локальний,
  назва акаунта/бакета та перевірка доступу).

## Дані та файли

- Усі дані зберігаються у `data/db.json` (створюється при першому записі).
  Якщо файлу немає — застосовується початковий набір із `data/seed.ts`.
  На Vercel цей файл лежить у тимчасовій ФС: замовлення та правки адмінки
  переживають редеплой лише в межах однієї збірки (окрема ризик-тема —
  потрібен постійний дисковий бекенд або база даних).
- Статичні зображення проєкту живуть у `public/images/` і ніколи не
  видаляються через адмін-панель.
- Завантажені адмінкою файли (товари, банери, карусель) йдуть у Cloudinary,
  якщо налаштовані `CLOUDINARY_*` (рекомендовано), інакше — у Cloudflare R2
  (`R2_*`); без обох — локально у `public/uploads/{products,banners,categories,branding,carousel}`.
- `data/db.json`, `public/uploads/`, `/photo/` і `/banner/` додано в `.gitignore` —
  у репозиторій потрапляє лише код і сід-дані.

## Постійне зберігання фотографій через Cloudinary (рекомендовано)

Адмін-панель завантажує фото через `POST /api/admin/storage` (multipart),
сервіс `lib/storage.ts` зберігає їх у Cloudinary і повертає постійний публічний
URL. Пріоритет бекендів: **Cloudinary → R2 → local**. Для великих файлів
(понад ліміт тіла Vercel 4.5 MB) використовується прямий upload із браузера
через `POST /api/admin/storage/sign` (підпис; API secret не залишає сервер).

1. **Cloudinary Dashboard → Product Environment Credentials** — скопіюйте
   `Cloud name`, `API key` і `API secret`.
2. **`.env.local` (локально) та Vercel → Project → Settings → Environment Variables:**
   заповніть `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`,
   `CLOUDINARY_API_SECRET`. Значення з секретами ніколи не мають префікса
   `NEXT_PUBLIC_`.
3. **Перевірка локально:** `/admin → Налаштування → Статус фотохмарки` показує
   режим (Cloudinary / R2 / локальний), назву акаунта та список невизначених
   змінних (лише назви, без значень). Кнопка **Перевірити зʼєднання** виконує
   `ping`. Або `npm run verify:cloudinary` — реальний upload → HEAD → replace →
   delete (секрети не друкуються).
4. **Міграція наявних файлів** із `public/uploads/`:
   ```bash
   npm run migrate:uploads:cloudinary              # dry-run
   npm run migrate:uploads:cloudinary:apply        # завантаження + оновлення data/db.json
   ```
   Скрипт нічого не видаляє, посилання у `data/db.json` змінює лише для
   успішно завантажених файлів і зупиняється, якщо змінні `CLOUDINARY_*` не заповнені.
5. **Локальний режим** лишається: без `CLOUDINARY_*` і `R2_*` файли пишуться
   у `public/uploads/`, старі посилання `/uploads/...` і `/images/...`
   працюють як раніше.
6. **Після редеплою** нові завантаження потрапляють у Cloudinary, а не у
   тимчасову ФС. Локальні копії в `public/uploads/` прибирайте лише після
   перевірки публічних URL — вони як і залишаються резервом.

## Постійне зберігання фотографій через Cloudflare R2 (альтернатива)

Використовується лише якщо Cloudinary не налаштовано. Адмін-панель завантажує
фото через `POST /api/admin/storage` (multipart), сервіс `lib/storage.ts`
зберігає їх у Cloudflare R2 за S3-протоколом (`@aws-sdk/client-s3`) і повертає
постійний публічний URL.

1. **Cloudflare Dashboard → R2 → Create bucket.** Наприклад `did-panas-images`,
   регіон automatic. Увімкніть **Public Development URL** (домен у форматі
   `https://pub-<hash>.r2.dev`) або підключіть власний домен у Settings →
   Custom Domains — це буде `R2_PUBLIC_BASE_URL`.
2. **R2 → Manage R2 API Tokens → Create API token.** Права лише
   *Object Read & Write* для конкретного бакета. Збережіть `Access Key ID` і
   `Secret Access Key`.
3. **R2 → Overview** — скопіюйте `Account ID`.
4. **`.env.local` (локально) та Vercel → Project → Settings → Environment Variables:**
   заповніть `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`,
   `R2_BUCKET_NAME`, `R2_PUBLIC_BASE_URL`. Значення з секретами ніколи не
   мають префікса `NEXT_PUBLIC_`.
5. **Перевірка:** `/admin → Налаштування → Статус фотохмарки` показує режим
   (R2 / локальний), назву бакета, публічний base URL та список
   невизначених змінних (лише назви, без значень). Кнопка
   **Перевірити зʼєднання** виконує `HeadBucket`.
6. **Міграція наявних файлів** із `public/uploads/`:
   ```bash
   npm run migrate:uploads              # звіт: файли, розмір, майбутні URL
   npm run migrate:uploads:apply        # завантаження + оновлення data/db.json
   npm run migrate:uploads:apply -- --verify  # + HEAD-перевірка публічних URL
   ```
   Скрипт нічого не видаляє, посилання у `data/db.json` змінює лише для
   успішно завантажених файлів і зупиняється, якщо змінні `R2_*` не заповнені.
7. **Локальний режим** лишається: без `R2_*` файли пишуться у `public/uploads/`,
   старі посилання `/uploads/...` і `/images/...` працюють як раніше,
   `next/image` отримує R2-домен через `images.remotePatterns`
   (читається з `R2_PUBLIC_BASE_URL` плюс шаблон `*.r2.dev`).
8. **Після редеплою** нові завантаження потрапляють у бакет, а не у тимчасову
   ФС. Локальні копії в `public/uploads/` прибирайте лише після перевірки
   публічних URL — вони як і залишаються резервом.

## Розгортання на Vercel

1. **Імпорт репозиторію:** на [vercel.com/new](https://vercel.com/new) підключіть
   GitHub-репозиторій `https://github.com/aleebaster/Did-Panas`. Framework:
   Next.js, всі налаштування за замовчуванням — Build & Output налаштовані
   самим Next.js.
2. **Environment Variables** (Vercel → Project → Settings → Environment
   Variables) — заповніть окремо від GitHub (не через .env.local у репо):
   - `ADMIN_LOGIN`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET` — доступ до `/admin`;
   - `NEXT_PUBLIC_SITE_URL` — https://<ваш-домен>;
   - `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` —
     постійне зберігання фото (рекомендовано);
   - `NOVA_POSHTA_API_KEY` — опційно, автопідказки Нової пошти.
3. **⚠️ Важливо: `data/db.json` не є постійною БД.** На Vercel файлова система
   read-only: `writeDbSync` кине помилку `EROFS`, тому замовлення та правки
   адмінки НЕ зберігаються між розгортаннями (стартує чистий `data/seed.ts`).
   Для production потрібна зовнішня БД (наприклад Upstash Redis або Neon) —
   це окрема задача, не реалізована в цій збірці.
4. **Ліміт тіла Vercel 4.5 MB** — обійдено для Cloudinary через прямий upload
   з браузера (`POST /api/admin/storage/sign`); для R2/локального режиму
   завантаження понад 4.5 MB падатиме — використовуйте Cloudinary.
5. **Деплой:** Vercel збирає і розгортає автоматично після push у `main`.
   Після деплою: `/admin → Налаштування → Статус фотохмарки` має показати
   Cloudinary, а завантаження фото — працювати.

```bash
npm run test:e2e
```

  валідація та ручний ввід без ключа.
- `tests/30-admin.spec.ts` — захист адмінки, вхід, CRUD товару/категорії/банера,
  збереження налаштувань, статус замовлення, вихід.
- `tests/40-home-carousel.spec.ts` — адмінка каруселі на головній та її рендер
  у магазині.
- `tests/50-promo.spec.ts` — промо-банери на головній.
- `tests/60-storage.spec.ts` — сервіс сховища: завантаження/заміна/видалення
  (моки S3 та Cloudinary), пріоритет Cloudinary, підписи, ліміти 8/10 МБ,
  магічні байти, поведінка без `CLOUDINARY_*`/`R2_*`, заборона видалення
  `public/images`, авторизація `/api/admin/storage`, відсутність секретів
  у клієнтському коді, збереження старих URL.
- `tests/responsive.spec.ts` — мобільна версія (Pixel 7): магазин і вхід в
  адмінку + вибір hero-зображення для 375/900/1280 px.
- `tests/global-setup.ts` / `tests/global-teardown.ts` — перед тестами
  `data/db.json` резервуються в системний tmp і скидаються до сіду, після
  тестів відновлюються: тести ніколи не змінюють ваші дані.

Конфігурація: `playwright.config.ts` — baseURL `http://localhost:3100`,
`webServer` сам запускає `npx next start -p 3100` (перевикористовує вже
запущений сервер), проєкти `desktop` (Desktop Chrome) і `mobile` (Pixel 7).

## Архітектура

- `app/(store)/` — публічні сторінки магазину (головна, каталог, товар, кошик,
  оформлення, підтвердження замовлення, про нас, доставка, контакти,
  політики).
- `app/admin/` — адмін-панель; захищена двома рівнями: `proxy.ts` (перевірка
  HMAC-cookie до рендеру) + `requireAdmin()` у layout.
- `lib/catalog.ts` — каталог із `"use cache"`; `lib/catalog-query.ts` —
  серіалізація фільтрів у query-параметри.
- `lib/db/` — читання/запис JSON-БД; `lib/actions/` — server actions.
- `components/` — UI магазину, каталогу, кошика, оформлення та адмінки.

## Правові примітки

- У публічному каталозі лише дві не-мухоморні позиції (кордицепс, їжовик);
  мухоморні фото лишаються в локальній папці `photo/` і не публікуються.
- Жодних медичних тверджень: тексти описують продукт як харчову добавку.
- Дисклеймер і юридичні тексти редагуються в **Налаштуваннях** та на сторінках
  `/privacy`, `/terms`.
